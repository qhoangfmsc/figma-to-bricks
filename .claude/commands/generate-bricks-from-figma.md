Owner decision (2026-10-27, confirmed in the chat): **this is the only workflow the owner starts, and it is automatic.** One link in, verified Bricks templates out; every decision follows the recommendation (the rules of `process/decide/` and `process/policy.json`); the owner reviews afterwards. The owner is **not asked questions during the run** and nothing waits for an OK, except the one Plan below (2026-10-29). The old question-by-question flow runs only when the arguments contain `--interactive` (then follow `process/SEMANTICS.md` section 3 and never sign off on your own).

**Owner decision 2026-10-29 (the Plan, one closed process):** the owner opens a new chat, types this command with a Figma link, gets ONE Plan, fills it, confirms it, and from then on everything is done by you until the page is finished. **Nothing is asked in the chat and no command is shown to the owner: the Plan file is the only place for questions, answers and the confirmation.**

1. **Plan.** Run `node process/auto.mjs "<url>"`. It reads every section, writes `process/work/<fileKey>/plan-<node>.md` and stops with exit code 3 (normal, not an error). Reply with a few lines only: the path of the Plan file (as a clickable link), the number of sections, what they become (FAQ accordion, menu, slider, tabs, buttons…) and how many groups of questions the file holds. **Do not list or ask the questions in the chat**; they are in the file under their own headings with a Figma link per item. Tell the owner to fill the file, change the line `Xác nhận: không` to `Xác nhận: có`, and say "xong".
2. **After "xong".** Run `node process/auto.mjs "<url>"` again. It reads the confirmed file (a wrong value stops it with the reason: report that reason in one line and wait), builds every section in one go (signed off as `owner (plan)`), then you run the fix loop, assemble the page and give the final report below. Blank values keep the safe default (`#`, empty alt, empty answer) and stay on the designer list; **never fill a value yourself or guess one**. If the owner types values in the chat anyway, write them into the file with `node process/scripts/plan.mjs "<url>" set <key> "<value>"` and ask nothing more.
3. After the confirmation the owner is not asked anything until the final report. "Done" means the page is assembled (`assemble-page.mjs <fileKey> <node> --final`, message HOÀN TẤT), not only the sections.
4. `--no-confirm` skips the Plan (the old fully automatic run); use it only when the owner asks. What is not built is listed in `process/BACKLOG-usable-output.md`; quote the items that touch this design in the report.

The first token of the arguments is the Figma URL; the rest are extra requirements (e.g. "this row is a slider").

**Figma is the reference.** What the eye sees in Figma is what the template must show, also when a section is cut out of its frame (a transparent section keeps the fill of its page frame). Every check compares with Figma's own render.

## Steps

1. **Pre-flight (the only things that may stop you).** The URL must have `node-id` (otherwise ask for the link of the selected frame). `.env` must have `FIGMA_TOKEN`. `docker compose ps` must show WordPress running; if not, `docker compose up -d`. Docker also runs the Playwright QA (image `f2b-qa:1`, built on first use): never open Chrome or any app on the owner's machine.
2. **Run** `node process/auto.mjs "<url>"` (progress, owner's decision 2026-10-28: the run writes `process/work/<fileKey>/progress-<node>.md` and prints one `[tiến trình]` line per change: % overall, sections done / total, per screen (desktop, tablet, mobile, widescreen) done / total, the section and screen in work, the step, a time estimate; read it with `node process/scripts/progress.mjs <fileKey>` and quote it in short updates; `regress.mjs` writes `progress-regress-<fileKey>.md` the same way). It works out what the link is (a whole page, one breakpoint frame, one section), builds **one template per section** (Menu, Hero, Problems… in page order), finds the tablet / mobile frames of each section and merges them as breakpoints, decides everything by rule, signs off as `autopilot`, pushes and verifies with Playwright (boxes, look vs Figma's render, covered layers, scroll, image weight, transparent areas, other browsers). `--plan` only lists the sections; `--only=<name>` runs one; a section that stops does not stop the others. A template the owner moved to the WordPress trash is replaced by a new one (not restored, not deleted for good). Output: `process/work/<fileKey>/page-<node>.md` and per section `scorecard.md`, `decisions.md`, `verify*.md`, `verify*.diff.png`. Do not use Figma MCP / `bricks-bridge` tools for this.
3. **Apply the extra requirements** the rules cannot know (a slider, a tag) with an `overrides.json` entry (`reason` quoting the owner), then re-run that section with `node process/run.mjs "<section url>" --from=build`.
4. **Fix loop (no questions; at most 3 rounds per root cause).** For every section whose verdict is FAIL or whose look score is above about 8/255:
   1. `node process/scripts/triage.mjs <section workspace>` → `triage.md`: the worst picture regions with the Figma nodes on them and the property that usually explains it, the real box mismatches grouped by check, structural problems.
   2. **Look at the picture**: `verify*.figma.png` next to `verify*.png` (lay a transparent Figma render over the page-frame fill of `context.json`), and `verify*.diff.png`. A box check alone is never a verdict, and a score is not trusted until the comparison is known to tell a wrong picture from a right one.
   3. Classify each real mismatch:
      - **a rule bug** (a Figma property dropped or mis-mapped: crop, stacking, fills, shadows, sizing, constraints…) → fix the module in `process/bricks/…` (read `process/AI-GUIDE.md` first), add a test in `process/test/`, `npm test --prefix process`, rebuild the section (`run.mjs … --from=build`);
      - **a wrong automatic decision** → fix the rule in `process/decide/` (or a default in `process/policy.json`), with a test;
      - **a limit** (text-engine difference ≤ 2.5px, live countdown, GLASS, an effect Bricks has no control for) → leave it; it stays listed;
      - **content the Figma file does not have** (URL, alt, tooltip copy, form action) → the designer list, never invented.
   4. **Regression guard after every rule change:** `node process/scripts/regress.mjs <fileKey>` rebuilds every section that has a scorecard and compares its numbers with `baseline.json`; a section that got worse means the change is reverted or narrowed. A rule in `decide/` or `auto.mjs` only reaches the sections by re-running `node process/auto.mjs "<url>"` and then `regress.mjs <fileKey> --no-rebuild`. When a round ends well: `node process/scripts/regress.mjs <fileKey> --save`. (First run of a page: `--save` once after step 2 to create the baseline.)
   Never hand-write Bricks JSON or edit `bricks.json`.
5. **Report once, in Vietnamese, short** (the only message the owner reads): a table per section (look score per frame, number of real mismatches, verdict from `verify.md`, template link); the usable-output audit in a few lines (headings and the `h1`, lists, links without URL, images without alt, blocks holding content, from `scorecard.md`); the automatic decisions that matter (link to `decisions.md`); the designer list; what stays as blocks, is not supported or is a limit (with the Figma value and what Bricks does); which rules you changed in this run and the regression result; the progress summary of the run (screens done / total, time taken). No proposals for extra work. Never claim a match from box checks alone.

## When you may talk to the owner during the run

For the Plan hand-off (exit code 3: point to the file, see above), and for a real blocker: no `node-id`, no token, Docker or WordPress down and not startable, `auto.mjs` reports BLOCKED (citations the code cannot verify) and you cannot fix it. Do not ask for other decisions, do not ask for an OK, do not paste `detections.md`. If something is unclear, take the recommendation and say so in the report.

## Deliverable, naming, reports, style (owner's decisions 2026-10-28)

- **Input** = this workflow + the Figma link. **Output** = every section as a Bricks template + ONE page that holds those templates in page order (`process/shared/deliverable.mjs`, written by `auto.mjs`; `node process/scripts/assemble-page.mjs <fileKey> <node> [--final]` rebuilds it). The page carries the design name as its title. The temporary preview page of the verify step is moved to the trash when a run ends (`regress.mjs`, `assemble-page.mjs`).
- **Template names:** `<design name> - <section>` (design name = the Figma file name, e.g. "Pagepeed Landingapge - Banner"). A section name that repeats on the page gets its number: "... - f-w 1", "... - f-w 2". A title the pipeline generated before ("Banner (figma 1583:582)") is renamed in place.
- **Reports:** one `[báo cáo] <n>/<total> - <screen>: xong giai đoạn 1,2,...` line per finished screen. Stages: 1 đọc Figma · 2 detect + quyết định · 3 export · 4 build · 5 push (đặt tên) · 6 verify · 7 sửa lỗi (after fix) · 8 ghép page + hoàn tất. Relay each line to the owner as it appears (Monitor on the run's log). When the fix loop is finished run `assemble-page.mjs <fileKey> <node> --final` and say clearly that the work is **HOÀN TẤT**.
- **Style = attributes first:** a Figma value is written to the Bricks control of that widget (Style > Layout / Spacing / Gradient / Transform / Border...), never into Custom CSS when a control exists. Custom CSS only where Bricks 1.9.8 has no control: `display: contents`, per-side inset strokes (several shadows), gradient strokes (`::before`), `align-self: stretch` in a row (the Bricks control also writes `width: 100%`), `list-style`, the gap of a button without icon (`iconGap` needs an icon), fractional rotation (Bricks keeps whole degrees), grid tracks, hiding a node on the wide frame. Each such use stays listed in the report.

## Rules (unchanged by autopilot)

- **Never run any git command that changes state** (commit, add, push, branch, stash, reset, PR). The owner does all git. Read-only `git status/diff/log` is fine.
- Exact to the pixel: every value comes from the Figma attributes. No screenshot-based values, no invented defaults. Anything that cannot be reproduced exactly goes in the report with the Figma value, never silently approximated. Tolerances are never loosened to make a check pass; the only documented classification is the **text-engine** class of `07-verify` (width / x of text, and the picture regions on it, within 2.5px), listed separately.
- Never invent content: link URLs, alt text, tooltip copy, form actions go to the designer list; the template gets the safe default (`#`, empty alt).
- Animation is noted in `animations.md` (`process/scripts/animations.mjs`), never built while painting.
- Usable output: `block` is for layout wrappers only; real headings, lists, buttons, images with alt where the rules decided them. Real Bricks components exist (done 2026-10-28): `button`, `form` (fields, consent checkbox, submit, per-field `errorMessage` from the designer's "Error message / X" text), menu `ul > li` + `text-link`. Any new component or rule goes through this same workflow and may only make a section's numbers equal or better (the regression guard checks it; a frame whose Figma render was not fetched shows as NOT MEASURED and counts as worse, never as an improvement). Accordion / tabs / slider are built only when the Figma file shows them or the arguments name the spot.
- Never print `.env` values. Do only what was asked.
- **Finish the workflow (owner's decision 2026-10-28):** the run is not over while a section of the page still has real mismatches that a rule fix can remove. Triage and fix every FAIL (3 rounds per root cause), rebuild, run the regression guard, and only then report. The report never ends with a "proposal for next work" or a question: whatever remains is listed as a limit (with the Figma value and what Bricks does) or on the designer list.
