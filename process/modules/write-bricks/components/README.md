# Bricks components: Figma pattern → real Bricks component

Mục lục: [../../../docs/INDEX.md](../../../docs/INDEX.md). Mỗi component: [../../../docs/widget-components/](../../../docs/widget-components/). Kệ ANV: [../../../docs/SHELF.md](../../../docs/SHELF.md).

The Figma files we get are not clean: a tooltip is an icon next to a label, a form is boxes + text + inputs, a button is a frame
with a text. A tree of blocks reproduces the picture but is not what a Bricks developer wants to edit. This folder holds the
**list of components we know how to build**, so the same pattern is always built the same way.

`SIGNAL_RULES` in `recognize-parts/kinds.mjs` is this list. Each component has `childComponent`: the parts that belong to it. A part is not a row here. `pagination_carousel`, `carousel_prev` and `carousel_next` belong to carousel. `tabs_bar` and `tabs_data` belong to tabs and to tab-switch. `thumb_scroll` and `track_scroll` belong to scroll.

How a node becomes a component (never automatic):

1. `steps/03-detect.mjs` proposes candidates (rules in `detect/rules/`, plus the AI pass) → `detections.json` / `detections.md`.
2. A **human** checks each one in Figma and sets `status`: `approved` or `rejected` (and fills `params`, e.g. the tooltip text).
3. `steps/04-export.mjs` downloads the Figma render of every approved `flat-image` (the only step that needs the network after detect).
4. `steps/05-build.mjs` turns only the **approved** ones into the component. Proposed / rejected stay blocks. An approved one that
   cannot be built (missing params, wrong shape) stays a block and is listed as a warning.
5. `steps/07-verify.mjs` checks the result (box, css, and component specifics such as the `data-balloon` attribute in the DOM).

Source of truth for Bricks behaviour is the **installed theme (1.12.3)** in `wp-content/themes/bricks/`, not the docs website
(the website describes newer versions).

"(basic)" = the simplest useful version: structure and the values Figma gives, nothing invented. A desktop-only frame still gets basic tablet and phone steps for large padding, margin and headings (`responsive/solo.mjs`); a pasted narrower frame keeps the values of that frame. A component is built only as its row and `CATALOG.md` say. An image is read on every pasted frame: another file with the same crop is `sources` at that breakpoint; a crop that moves stays that frame's own element. `planned` = known need, not built: approving it only produces a warning, the node stays a block (none left at the moment).

## Add a component

1. Read how Bricks 1.9.8 does it in `wp-content/themes/bricks/includes/elements/<element>.php` (controls, `render()`), and the
   theme CSS that element gets by default (`assets/css/frontend.min.css`): theme defaults leak unless you override them explicitly.
2. Copy `tooltip.mjs` (attributes on an existing element) or `button.mjs` (a different element, merging children). Fill `check()`
   (can this node become it? return the reason if not) and `apply(ctx, det)` (write `ctx.s`; return `{ attrs }` for DOM checks).
3. Register it in `index.mjs` and add a row above.
4. Add a candidate rule in `detect/rules/` if it can be recognized from the tree (rules only propose; keep them conservative).
5. Add tests in `test/pipeline.test.mjs`, then try it on a real section: approve one candidate in a **copy** of the workspace's
   `detections.json`, run `--from=detect`, read `verify.md`. Theme-default leaks show up as mismatches (this is how the button's
   `gap` and `letter-spacing` were found).
6. Update this table, the "limits" column, and `process/docs/AI-GUIDE.md` if the workflow changed.
